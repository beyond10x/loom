## Decisions taken during the wave

- U1's security review found nothing to change before the merge. Its one note (the standard-error
  line prints the turn's error unescaped, and part of that text can be model output) is filed as
  the draft `story:a2a-stderr-line-escapes-error-text`.
- U3's adversary pass found two introduced defects, both taken into a U3 fix round by the wave
  lead: a run ended at its deadline whose pod is still readable reported `lastRun.reason` `Error`
  rather than `DeadlineExceeded` (the code is fixed, keeping the pod's exit code), and a
  `runDeadlineSeconds` above 9223372036 was admitted although a Kubernetes duration of that many
  seconds wraps (refused `Malformed` beside the zero bound, declared in ESS). The first edits the
  observation path of `crates/loom-operator/src/reconcile.rs`, which U4 then builds on.
- U3 fix round 1: ESS 0.86.0 cannot bound an `Integer` field (`minimum` is an unknown field), so
  the `runDeadlineSeconds` upper bound is stated in the `ScheduleSpec` comment and enforced by
  admission. The same overflow in `startingDeadlineSeconds` (pre-existing) rides along in U4.
- U2 adversary pass: a sending `agent run` of a spec with loops still needed `list`, `get` and
  `search` (pre-existing, named by the story's Outcome) and an `AgentServe` resource with no loops
  was admitted and then failed at start (widened by U2). Both fixed in U2 fix round 2: a run reads
  only the channel's `write`, and `AgentServe` with no loops is refused `Malformed` at
  `spec.agent.loops` (a `Command` resource still admits it). Help texts for the serve exit code
  and the run defaults were corrected; the note that the RunOnce scenario cannot fail for this
  behaviour is accepted, `agent_run.rs` holds it. Three existing operator fixtures gained a
  `loops` block.
- U4 adversary pass: four findings (a CronJob given back while still terminating read
  `Scheduled`, a round failing after the CronJob apply kept the wait, a predecessor named beside a
  live CronJob, the design table missing the starting-deadline bound), all fixed in U4 fix round 1.
  `status::Scheduled` changes shape; `b10x-loom-operator` is not published and no consumer names
  it, so the release carries no `**Breaking:**` bullet for it.
- U2 merges last: the integration branch is merged into its tree and the generated code and
  reference pages are regenerated there once over both ESS changes.
- Release go (the orchestrator, 2026-11-05): "go now for loom 0.57.0 merge through the bot, tag
  and release on green PR CI, without asking again. Check `gh pr checks <n> -R beyond10x/loom`
  yourself before merging", then verify the release, write the announcement and finish the trees.
