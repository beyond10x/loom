| # | file:line | Verdict | Origin | What was measured | What reaches it |

| 1 | `crates/loom-commission/src/runtime.rs:1098` | CONFIRMED | pre-existing | When `check_authority` allows, the request goes straight to `effects.invoke` at :1126. Nothing reads the case revision in between. The run-loop case is red with `[(7, 8)]`, here and on the base | Any writer that moves the case during `decide`. The runtime docs say other writers move cases (runtime.rs module docs, items 2 and 8a: "somebody else moved the case"). My test creates the move; I saw no real instance. I found no production effect port that re-checks `expected_case_revision`, but I did not search exhaustively |
| 2 | `crates/loom-commission/src/runtime.rs:1391` | CONFIRMED | pre-existing | When the resume is allowed, `resume_run`, then `take`, then `invoke` at :927 run without reading the case again. The resume case is red with `[(7, 8)]`, here and on the base | Same as #1. Per AGENTS.md § Mandate, `resume --mandate` writes the approval to the state-dir log inside `decide`, which makes the window longer |

Why it matters more now: the unit's doc (`ports/authority.rs:9-10`) and its AGENTS.md row tell a provider it "can allow one request at one case revision and refuse the same action at the next". Because of this gap, a grant tied to revision 7 still gets the effect performed on a case at revision 8.

Suggested fix (not applied): after the allow and right before invoking, read `current_revision` again or re-run `revalidate`. On a move, treat the request as stale in the run loop, and refuse it as `CaseMoved` on resume. Some window remains unless the effect port itself refuses a request whose `expected_case_revision` is no longer current.
