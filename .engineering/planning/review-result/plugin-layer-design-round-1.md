needs-revision

connectors-cli-reads — the five actions map to CLI discovery commands (`adapters list`, `connections list`, `operations list`, `operations describe`) and to an operation "the source declares", but `ConnectorInvoker::invoke(binding, request)` performs one operation named by a fixed `ActionBinding`, and a read's `Performed` must name a completed audit record. Four of the five actions have no binding and no audit record, and a binding set fixed per commission cannot take an operation discovered at run time. The body should split a plain CLI client (list, describe, invoke) from the `ConnectorInvoker` impl over it, and bind only `entity.*` to named operations — `.engineering/planning/story/connectors-cli-reads.md:32-35`, `crates/loom-commission/src/ports/connector.rs:32-41`, `crates/loom-connectors/src/lib.rs:209-216`

connectors-cli-reads — `story:slack-plugin`'s `source.poll` reads `conversations.list`, `.history` and `.replies` "all through the CLI invoker", outside any run. The only surface this story produces is a `ConnectorInvoker`, whose `invoke` needs an `AdmittedRequest` that "only the runtime makes" (`AdmittedRequest::new` is `pub(crate)`). No item in the set produces a read surface that a poll outside a case can call, so the poll cannot be built as written. The fix is the same plain client, exported from the one crate that calls Connectors, with `story:slack-plugin` saying it uses it — `.engineering/planning/story/slack-plugin.md:24-26`, `crates/loom-commission/src/ports/effect.rs:42-49`

connectors-cli-reads — the ESS-first line leaves the binding's owner open ("the commission `responsibility` domain's connector binding, or a `loom.plugin` binding table"). The second option lives in a domain that `story:plugin-host` creates, and plugin-host `depends_on` this story, so choosing it turns the order round. The body should name the commission `responsibility` domain, which exists, or move the binding table into plugin-host's declaration list — `.engineering/planning/story/connectors-cli-reads.md:22-23`, `.engineering/planning/story/plugin-host.md:21-22`

plugin-host — the `turn` hook "runs the governed loop (`Loom::run_loop`)", which stops at the first admitted selection and returns a `ProposedAction` (governed.rs:150-160). The read is performed by Commission's `run_until_blocked` through an `EffectPort`, which here would be `ConnectorEffects` over bindings, a governor admitting `inbound-answer@1`, an authority provider and a run store. `ConnectorEffects` has no production caller, only testkit tests, and no item composes this wiring or the step that submits `source_read` evidence from a `Performed` read. Without that step, `inbound-answer`'s outcome `proposed` (requires at least one source read) is never reached. The turn needs a stated composition and a stated evidence submitter, as `clock.rs` is for the clock — `.engineering/planning/story/plugin-host.md:31-33`, `crates/loom-executor/src/harness/governed.rs:150-160`, `.engineering/planning/story/inbound-answer-protocol.md:24-28`

slack-plugin — the ESS-first line says "No new noun beyond `loom.plugin`", but the config (adapter alias, connection id, bot user id, weights, allow and deny lists, `min_age`, seed) is a noun that plugin-host's domain list (Item, Intent, Projection, Proposal, PluginState, Record line) does not hold. It would be a hand-written type beside ESS, which AGENTS § ESS forbids. The body should add a Config declaration, either to plugin-host's `loom.plugin` or to a slack domain of its own — `.engineering/planning/story/slack-plugin.md:20`, `.engineering/planning/story/slack-plugin.md:30-31`, `.engineering/planning/story/plugin-host.md:21-22`

slack-plugin — the fixture acceptance says "nothing else is invoked" beyond the three polling reads. Yet the 3 record lines come from governed turns on `inbound-answer@1`, whose `proposed` outcome requires a source read through `entity.*`. The acceptance contradicts the protocol it depends on, so the fixture must either name the turn's reads or say the record stops short of `proposed` — `.engineering/planning/story/slack-plugin.md:32-34`, `.engineering/planning/story/inbound-answer-protocol.md:26-28`

inbound-answer-protocol — bundling `inbound-answer@1` into `ProtocolCatalog::bundled()` puts a plugin-only protocol in the catalog that `loom-intake-router` shows the model (`classify_with_catalog` builds its registry from every entry) and that `protocols list` prints. A user `run` intent can then be routed to a protocol with no local executor, which ends in `NoLocalExecutor`. The plugin's `task` path (router pick) can also select it. The body should say whether the catalog is split (a plugin catalog beside the bundled one) or the router excludes it — `.engineering/planning/story/inbound-answer-protocol.md:29`, `crates/loom-protocols/src/lib.rs:91-103`, `crates/loom-intake-router/src/classify.rs:119-140`

epic:plugin-layer — acceptance line 2 ("a second run over the same fixtures records no new proposal") is attributed to `story:plugin-host`. Host tests use a fake plugin, and the Slack fixture exists only once `story:slack-plugin` lands, so the reader is attributed to a producer that does not make it. Re-attribute the line to slack-plugin, or add it to that story's acceptance — `.engineering/planning/epic/plugin-layer.md:25`, `.engineering/planning/story/slack-plugin.md:32-34`

plugin-measurement — its acceptance "`story:yaml-only-plugin` cites the page" reads an artifact that is not in the store or in the set (`aep plan artifact show story:yaml-only-plugin` finds no such artifact). That line belongs to yaml-only-plugin's own acceptance, once it exists, and should leave this story — `.engineering/planning/story/plugin-measurement.md:29`

What I read: 7 artifacts shown whole (`aep plan artifact show`), plus `aep plan artifact relations`, `graph` and `validate` (valid; three unrelated prose-only reviews). I walked 17 edges, including `vision:O1` outside the set, and found no cycle. The chain is [protocol, reads] → host → slack → measurement, so the two roots run in parallel. I traced 9 acceptance reads to producers in the set. Edges record 6, directly or through `plugin-host`; the exceptions are the epic's line 2 and the `yaml-only-plugin` read above. I also read AGENTS.md (Rules, ESS, Connectors, Intake), `hook.rs`, `governed.rs`, `loom-protocols/src/lib.rs`, `loom-connectors/src/lib.rs`, `ports/connector.rs`, `ports/effect.rs`, `classify.rs` and `system-query/1.yaml`.

What I could not establish:
- How Canon expresses "a proposal" as evidence for the outcome `proposed`. I did not find a producer for it, but I did not read Canon's claim grammar.
- Whether the real `connectors` CLI prints an `audit_ref` on `operations invoke --output json`. The invoker's read path needs one.
- Out of my lane: `crates/loom-cli/tests` and `crates/loom-governor/tests` use `ProtocolCatalog::bundled()` and may break when the catalog grows. That is scope or parallel safety, and it did not set my verdict.
- Out of my lane: the connectors-cli-reads scope omits `AGENTS.md` § Connectors, though it adds a second invoker.
